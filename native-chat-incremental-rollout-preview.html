What changes for users in each rollout step

Proposal walkthrough, not an implementation. The normal terminal experience remains available. Native chat appears only for a developer who has explicitly opted into the existing experimental setting and whose host/provider passes its capability checks.

1

Existing user: nothing changes

Current terminal-owned sessions remain compatible.

Who sees this

Everyone, including users who never enabled experimental features.

What happens

Open a worktree and use the normal agent terminal exactly as today.

Codex terminalCurrent behavior

Your terminal transcript and composer stay the primary surface.

2

Developer opt-in: native chat becomes an option

No new toggle is proposed; the existing opt-in and host capability decide eligibility.

Who sees this

A developer who deliberately enabled experimentalNativeChat, on a host/provider that advertises structured chat.

What happens

The user can choose native chat or continue using the terminal. Unsupported hosts stay on the normal path.

3a

Launching native chat opens the chat you created

The new structured session becomes the visible active tab as soon as the host publishes it.

Who sees this

An opted-in developer who chooses Codex or Claude from the New tab menu.

What happens

The app does not leave the user looking at an older terminal. The newly created native chat tab is activated and ready for the first prompt.

Codex ChatNew active tab

The tab selected by the user is the tab rendered on screen; durable creation without visible activation is treated as a launch failure.

3

Native chat: structured operations

The host owns the durable session; the workspace shell remains available alongside it.

Who sees this

A user who selected native chat in step 2 and completed a proven structured launch.

What happens

Prompts, approvals, questions, cancellation, images, and options use the structured session rather than a PTY write.

Native agent chatHost-owned

Conversation history is replayable after reconnect. Workspace terminal remains a separate action.

4

If structured launch fails: stay recoverable

No silent runtime switch and no lost prompt when delivery is uncertain.

Who sees this

A developer who opted in, but the host/provider could not prove a safe structured owner.

What happens

The app explains the failure and preserves a recoverable owner. An explicit terminal fallback may be offered only after this proposal is approved.

5

Qualified handoff: switch only while idle

A real TUI ↔ native cycle is enabled only after provider-specific proof.

Who sees this

An opted-in developer using a provider and host that passed the full handoff capability probe.

What happens

Pending approvals, questions, background work, and unsaved composer text block the switch. The user can keep using the current surface.
